How Bare Metal works

A guided tour of the code: one HTML file that impersonates an interviewer, runs your Python in the browser, and refuses to autocomplete anything.

subject: index.html (~1,600 lines, vanilla JS) · repo: demart78/Template · written 2026-07-04

1 · Background

Why this program exists, and what it refuses to do

Coding interviews at big tech companies still happen in a shared plain-text editor: no autocomplete, no syntax highlighting, no way to run anything, and a requirement to narrate your thinking out loud while a stranger watches. Meanwhile, the day job of the person being interviewed increasingly consists of steering AI coding tools. The skills have diverged. Bare Metal exists to close that gap: it recreates the interview's hostile environment on purpose, then wraps it in the things a real interview can't give you — a coach that teaches, a debugger that shows you your program's state changing line by line, and drills that train pattern recognition directly.

The engineering constraints shape everything you'll see in the code:

  • One file, no server. The entire app is a single index.html. There's no build step, no npm, no backend. Every capability has to come from the browser itself or from an API the browser can call directly.
  • Two AI vendors, called from the browser. Claude (Opus 4.8) plays the interviewer, grader, problem author, and distiller. Gemini is used for exactly one thing: natively watching YouTube videos. Both keys live in localStorage and requests go straight to each vendor — there is no middleman that could see them.
  • Python execution without a Python server. Syntax checking and the step-through debugger run real CPython inside the browser via Pyodide (CPython compiled to WebAssembly), lazy-loaded only when first needed.
  • The friction is the product. The editor is a bare <textarea>. This is not a missing feature; it is the feature. Every design decision distinguishes productive friction (keep) from incidental friction (remove).

2 · Intuition

Three ideas carry the whole design

Idea 1: The client decides when; the model decides what

The most interesting architectural choice is how the "interviewer who interrupts you" is built. A naive design would ask the model to decide when to speak — poll it every few seconds with "anything to say?" That would be slow, expensive, and erratic. Instead, Bare Metal splits the job:

Deterministic JavaScript decides when to interrupt (cheap, instant, predictable). The model decides what to say (contextual, adaptive). Neither does the other's job.

Let's make this concrete. Suppose you type for i in range(len(intervals)): and keep going. Within four seconds, the watcher's regex for range(len( matches. That trigger fires once per session (a Set remembers), builds a payload containing your full code and everything you've said since the interviewer last spoke, and sends it with a private stage direction: "probe the loop bounds — off-by-one is the classic autocomplete-era failure — but only if the concern actually applies to what they wrote." Claude sees your actual code and decides whether the concern applies. The interruption arrives as one or two spoken sentences, not an essay.

Idea 2: Two modes are one machine with different knobs

Coach mode and Interview mode share every line of session machinery — the same triggers, the same chat, the same editor. What differs is a handful of parameters and, crucially, the system prompt:

This is why the "I'm ready — start the test" button is a one-liner in the code: it just calls startSession("test"). Same machine, different knobs, fresh problem.

Idea 3: The debugger is a recording, not a live process

Real debuggers pause a live process. Bare Metal's step-through debugger does something simpler and, for learning, better: it runs your function to completion once under CPython's tracing hook, recording a snapshot of every executed line — line number, function name, and the repr() of every local variable. Stepping "forward" and "backward" is then just moving an index through an array of snapshots. Time travel is free because nothing is actually running.

The 500-step cap is the infinite-loop defense: `while True: pass` produces a line event per iteration, hits the cap, and stops with a clear message instead of freezing the tab.

One example: trace merge([[1,3],[2,6],[8,10]]) against a correct merge-intervals solution and you get 20 steps. Step 4 shows start=1, end=3, out=[]; step 5 shows out=[[1, 3]] with out highlighted because its value changed. The bug you can't see in your head becomes a frame you can point at.

3 · Code

A walkthrough of the file, top to bottom

Everything lives in index.html: a <style> block, three screen <div>s (setup, interview, debrief) toggled by display, and one <script>. The script reads in this order:

Data: the problem bank and the trigger table

PROBLEMS is an array of 15 objects (id, topic, title, statement, examples, constraints, target). CODE_TRIGGERS is the interruption table — each entry pairs a detector with a stage direction for the model:

{
  id: "range-len",
  test: c => /range\(\s*len\(/.test(c),
  note: "Candidate wrote range(len(...)). Probe the loop bounds: off-by-one
         is the classic autocomplete-era failure..."
}

Adding your own interruption is adding an object here. The note is never shown to you — it's whispered to the interviewer.

State: one object, plus a session fence

All mutable state hangs off a single object S: mode, topic, the current problem, clocks, hint count, the narration buffer, the transcript, and the Claude conversation history. Two fields exist purely to prevent race bugs:

sessionId: 0,  // bumped on every new session; stale API replies are dropped

Every async operation captures S.sessionId (and a reference to the current history array) before awaiting. If you end a coach session while a reply is still in flight, the reply comes back, notices the world has moved on, and discards itself instead of injecting a ghost message into your fresh interview:

const hist = S.history; // bind to THIS session's history
hist.push({ role: "user", content: userMsg });
...
const text = await callClaude(...);
if (sess !== S.sessionId) return; // session switched mid-flight — drop it

The conversation: apiRequest → callClaude

apiRequest is the one place that touches the network: a fetch to api.anthropic.com/v1/messages with the key, version header, and the CORS opt-in header (anthropic-dangerous-direct-browser-access). It logs every call — latency, input/cached/output tokens — to the debug panel. callClaude layers the conversation on top: it appends your event as a user turn, sends the entire history plus the system prompt, and appends the assistant reply. A failed call pops the user turn back off so a network blip can't poison the transcript.

The cost trick is one line:

system: [{ type: "text", text: systemPrompt(),
           cache_control: { type: "ephemeral" } }],

systemPrompt() is deterministic for a given session (persona + problem text), so every call after the first hits Anthropic's prompt cache and the big prefix bills at roughly a tenth of the normal input price. Interruptions run at effort: "low" for snappy replies; the final grading runs with adaptive thinking at effort: "high".

Deciding when to speak: watch()

A 4-second interval does three checks in priority order: (1) any un-fired code trigger whose regex now matches, (2) silence — no keystroke and no narration for longer than the mode's threshold, with a 90-second cooldown so it doesn't nag, (3) a gentle check-in if six minutes pass with nothing else. Whichever fires calls interviewerSpeak(trigger, note), which assembles the payload:

[TRIGGER: CODE PATTERN OBSERVED]
[NOTE FOR YOU: Candidate wrote range(len(...))...]
[ELAPSED: 08:12 / 25:00] [HINTS REMAINING: 3]
[CODE SNAPSHOT]
...your editor contents...
[NARRATION SINCE LAST EXCHANGE]
[03:41] I'm sorting by start time first...

Notice the narration buffer drains into each payload — the model always knows what you've said since it last spoke, and whether your code changed.

The execution sandbox: Pyodide, checkSyntax, and TRACER_PY

loadPyodideOnce() injects the Pyodide script tag on first use (~10 MB, then browser-cached) and memoizes the promise; a failed load resets the memo so you can retry. Syntax checking is CPython's own compile() wrapped to return structured JSON: {ok: false, line: 3, msg: "expected ':'"}.

The tracer is a Python program stored in a JS template string. Its heart is the trace hook:

def _tracer(frame, event, arg):
    code = frame.f_code
    if code.co_filename != "solution.py" or code.co_name == "<module>":
        return None          # only trace YOUR functions, not machinery
    if event in ("line", "return"):
        _steps.append({
            "line": frame.f_lineno,
            "locals": {k: _fmt(v) for k, v in frame.f_locals.items()},
            ...
        })
        if len(_steps) >= 500:
            raise _Limit()      # infinite-loop circuit breaker
    return _tracer

Three details worth noticing. First, the filename filter: your code is compiled with the filename solution.py, so the hook can ignore every frame that isn't yours. Second, the <module> exclusion: the expression that calls your function runs in a module-level frame whose "locals" are the entire namespace — recording it would bury the signal, so only real function frames are kept. Third, locals are stored as strings (repr, truncated at 140 chars), because live Python objects can't survive the trip across the WASM boundary — but their printed form can, as one JSON document.

On the JavaScript side, gotoStep(i) is pure rendering: highlight line steps[i].line, list steps[i].locals, and mark any variable whose string differs from step i−1 — that's the orange "this just changed" highlight, computed by nothing fancier than string comparison.

Generation surfaces: problems, sprints, cards

Three features ask Claude to produce data rather than conversation, and all three use structured outputs (output_config.format with a JSON schema) so the reply is guaranteed parseable — no regex-scraping model prose:

  • generateProblem(topic) — authors an original LC-medium variant, told which titles you've seen recently (from localStorage) so it avoids resembling them.
  • startSprint() — asks for 8 rounds of {statement, options[4], answer_index, tell}; the quiz UI is then a dumb renderer over that array.
  • distillRequest(topic, source) — produces a pattern card in a fixed markdown skeleton. Its source can be pasted notes, a finished session (problem + your code + the grader's report), or notes Gemini extracted by natively watching a YouTube URL — the one place a second vendor enters, via geminiWatch(), which passes the video URL as a file_data part.

Grading: submitSolution()

Submission assembles everything the grader needs to be fair: the final code, the complete timestamped transcript (your narration, its interruptions, hints spent), and — so it never has to guess — an objective compile result from a final automatic checkSyntax run: PASSES or FAILS — SyntaxError line 7. The system prompt's SUBMIT section demands a hand-trace of your code against the printed examples before any verdict is allowed. If the network fails at this moment, the machinery un-pops the payload, restarts the clocks, and lets you press submit again — a 25-minute session is never lost to one bad request.

where to poke first If you want to modify the app, the three arrays near the top of the script — PROBLEMS, CODE_TRIGGERS, SPRINT_PATTERNS — are designed as extension points. Add an entry; no other code changes needed.

4 · Quiz

Check your understanding

Five questions, medium difficulty. Click an answer to see how you did.

Question 1
You end a Coach session by clicking "I'm ready — start the test" while the coach's reply to your last trace is still in flight. Why doesn't that reply appear inside your new interview?
The session fence. Nothing is cancelled — cancellation is fiddly and unnecessary. Instead, every async path binds const hist = S.history and const sess = S.sessionId before awaiting. startSession() replaces the history array and bumps the id, so the late reply pushes into an unreachable array and the sess !== S.sessionId guard skips rendering. The stale work completes harmlessly.
Question 2
You trace f() where the body is while True: pass. What happens?
The circuit breaker is the trace itself. sys.settrace fires the hook on every executed line, so a spinning loop feeds its own shutdown: 500 events arrive in milliseconds, _Limit propagates out of eval, the finally clears the trace hook, and JavaScript gets {error: "stopped at 500 steps..."}. Pyodide does run on the main thread — which is exactly why the cap matters — but there is no built-in watchdog; option A is what would happen without the cap.
Question 3
The trace hook ignores frames where co_name == "<module>". What would you see in the variables panel if it didn't?
Signal over noise. Your call (merge([[1,3],[2,6]])) is evaluated in a module-level frame whose f_locals is the exec'd namespace — containing merge itself and anything else you defined. Recording it would put <function merge at 0x...> in the variables panel at step 1. The filter keeps only frames of functions you wrote, which is where the learning is.
Question 4
Why does the request put cache_control: {type: "ephemeral"} on the system prompt, and when does that cache stop helping?
Prefix caching. The Messages API is stateless — full history is resent every call — but the provider caches the rendered prefix at the breakpoint. An interruption-heavy session makes 10–15 calls sharing the same big system prompt; caching turns most of that repeated input into ~10%-price reads. Any byte change in the prefix (new problem, switched mode → different systemPrompt() output) means a cache miss, which is why each session pays one full-price write and then coasts.
Question 5
Code-pattern triggers fire at most once per session (firedTriggers is a Set). What actually goes wrong without that?
Triggers are level-detectors, not edge-detectors. The regex tests the current editor contents, which still match 4 seconds later. Without the Set, the condition stays true and the probe repeats forever. Marking each trigger as fired converts a level ("this pattern exists") into an edge ("this pattern was first observed") — the same reason hardware interrupts get acknowledged.
